# 阶段三里程碑报告

## 1. 概述

本文档总结 ZeroShotVDR 在 Phase 3 的完成情况，主要包括：

1. 在修正页面身份协议后的稳定基线全量评测；
2. bad case 分析与数据集标注审计；
3. 下一阶段 Phase 4 改进方向的决策。

本项目面向 MMLongBench 上的零样本视觉文档检索任务，采用 ColPali 作为基线检索模型。

---

## 2. 阶段三已完成内容

到本阶段结束时，基线系统已经不再只是“能跑通”，而是成为了一条稳定、可分析、可复现实验结论的评测流水线。

### 2.1 端到端基线管线

我们已经完成了基于 ColPali 的页级检索基线系统，包含以下模块：

- 离线页面索引构建；
- 文本查询编码；
- late interaction 的 MaxSim 打分；
- Recall、Precision、MRR、nDCG 等指标的自动计算；
- 全量运行结果的落盘与报告导出。

主执行入口为：

- `scripts/run_step3_eval.py`

分析入口为：

- `scripts/run_step3_analysis.py`

### 2.2 阶段三中完成的工程修正

在最终 full run 前，我们发现并修复了两个关键问题：

1. **长上下文 DocumentQA 中页面身份不稳定**
   - 旧的 `doc_id/page_idx` 契约在不同原始样本之间并不是全局稳定的；
   - 我们改为从原始图片路径重建稳定页面身份，并为每条 Query 显式绑定精确候选页面集合。

2. **分析层被无效 ground truth 污染**
   - MMLongBench 中有一部分查询的答案页标注为空或无效；
   - 我们将这类样本单独标记为 `no_ground_truth`，而不是继续混入真实 bad case。

这两项修正都是必要的。若不先完成它们，基线指标和 bad case 结论都会缺乏可信度。

## 4. 数据集审计与主汇报口径

### 4.1 无效或缺失标注

我们确认，在 15,577 条查询中，有 1,192 条缺失或包含无效 ground truth，主要表现为：

- `ans_page_list` 为空；
- `ans_page_list = [-1]`；
- `ans_page_list` 中包含 `0`；
- 标注目标页号超出当前 `page_list` 的覆盖范围。

这些样本现已单独导出到：

- `outputs/eval_reports/step3_docqa_full_dual3090_stable_page_ids/analysis/no_ground_truth_cases.csv`

### 4.2 主比较口径

为保证方法比较公平，我们固定以下主汇报口径：

- **主表只统计 14,385 条具有有效页级标注的查询**；
- 全量查询指标仅保留为附录级别的完整披露结果。

必须这样做的原因在于：当前指标实现会将空 relevant set 记为完美召回和完美 MRR；如果把这类样本直接混入主表，会系统性高估模型表现。

这说明稳定页面身份的重构不仅让系统更整洁，也让评测结论真正变得可信。

## 5. Step 3.2 的主要发现

分析产物存放在：

- `outputs/eval_reports/step3_docqa_full_dual3090_stable_page_ids/analysis/`

### 5.1 难点热点

当前最困难的 slice 集中在长上下文场景：

- `slidevqa/K128`
- `slidevqa/K64`
- `slidevqa/K32`
- `mmlongdoc/K128`
- `longdocurl/K128`

这些 slice 同时具备更大的候选集规模，以及更强的视觉相似页面干扰。

### 5.2 真实 bad case 比例

在将 `no_ground_truth` 样本剥离后，当前有：

- 14,385 条可用 ground truth 查询；
- 2,636 条 Recall@10 < 1.0 的真实 bad case；
- 真实 bad-case rate = 18.32%。

这一比例明显比“把所有无效标注查询都算成失败”更诚实，也更适合作为后续方法改进的依据。

### 5.3 失败类型

当前稳定基线的失败模式主要有三类：

1. **大候选集下的 miss_top10**
   - 在 slidevqa 长上下文中尤其明显；
   - 常见原因是多个 slide 在版式上高度相似，但局部细节不同。

2. **多页部分召回（multi-page partial recall）**
   - 在 longdocurl 和 mmlongdoc 中较为常见；
   - 说明相邻页或多页联合证据确实重要。

3. **邻页混淆（neighbor-page confusion）**
   - 目标页与高排名干扰页往往只在局部表格数值或相邻页面细节上不同。

## 6. Step 3.3 决策：Phase 4 改进方向

我们对项目计划中提出的两条候选方向进行了对比：

- 方向 A：查询感知的自适应索引压缩
- 方向 B：两阶段粗精检索

### 6.1 为什么选择方向 B 作为 Phase 4 主线

我们最终选择 **方向 B** 作为 Phase 4 的主线，原因有三点：

1. **它与当前观察到的失败模式更加直接对应。**
   当前 hardest slices 主要表现为大候选集下的 `miss_top10`，尤其集中在 slidevqa K32-K128。

2. **它与现有实现距离更近。**
   当前代码已经具备：
   - `IndexStore` 中的 mean-pooled page view；
   - `RetrievalPipeline` 中预留的 `mean_pool_topN` 候选策略。

3. **它在创新性与实现风险之间的平衡最好。**
   直接做一个固定 top-50 reranker 过于常规，但基于查询自适应候选规模和邻页扩展的 coarse-to-fine 方案，既可实现，又能从 Phase 3 分析中得到充分动机支持。

### 6.2 为什么不把方向 A 作为 Phase 4 主线

方向 A 仍然有价值，尤其是当前索引体量较大。但它不适合作为当前阶段的主线，主要因为：

- hardest slices 依赖细粒度视觉证据；
- 激进的 patch pruning 容易进一步伤害当前最难提升的样本；
- 它会同时牵动存储、打分与重建索引三部分，工程风险更高。

因此，方向 A 暂时被降级为补充方案或未来工作，除非后续时间足够充裕。

---

## 7. 计划中的 Phase 4 方法

当前选定的 Phase 4 方法为：

**查询自适应的两阶段粗精检索**

计划设计如下：

1. **第一阶段：粗检索**
   - 对查询构造 mean embedding；
   - 使用页面 mean-pooled embedding 做快速粗筛；
   - 保留一个自适应规模的候选集，而不是固定 top-50。

2. **第二阶段：完整 MaxSim 精排**
   - 仅在缩小后的候选集上执行原始 late-interaction 打分。

3. **邻页感知扩展**
   - 对 coarse stage 高排名页面做小窗口邻页扩展；
   - 直接针对多页证据需求和邻页混淆问题。

预期成功标准为：

- 在有效标注查询上保持或提升检索质量；
- 降低长上下文 slice 的检索延迟；
- 在固定评测口径下给出公平的 baseline vs. improved 对比。
