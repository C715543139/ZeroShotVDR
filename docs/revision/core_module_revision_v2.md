# ZeroShotVDR 核心模块修订建议 v2

## 1. 说明

本次修订基于对修改后 `docs/Project_Plan.md` 的第二轮审查形成。

与 v1 不同，本轮默认接受一个前提：

- 设计文档可以写得比修订文档更具体，包含较详细的模块拆分、接口草案和实现约束。

因此，v2 不再讨论“设计文档是否写得过细”，而只关注以下问题：

1. 设计文档在语义上是否自洽。
2. 设计文档是否真正满足 v1 所强调的修改方向。
3. 除粒度问题之外，当前方案还存在哪些会影响落地或扩展的风险。

---

## 2. 第二轮审查结论

在不再纠结文档粒度的前提下，当前 `Project_Plan.md` 已经比原版更接近预期，主要体现在：

1. Baseline 路线已明确收敛到 DocumentQA，而不是继续围绕 PDF-only 路径展开。
2. 模块组织已经与当前仓库的 `src/zeroshot_vdr/` 包结构对齐。
3. 检索层和评测层的分工比原版更清楚，扩展空间也更合理。
4. Windows 下 `datasets` 与 `torch` 的导入约束已经进入架构层面的说明，而不再只是环境备注。

整体判断是：方向基本正确，但仍存在几类未收口的问题。这些问题不属于“写得太细”，而属于“设计语义尚未完全闭合”。

---

## 3. 仍需处理的核心问题

### 3.1 命名体系仍未完全统一

当前文档中，同一层级的概念仍存在不同命名方式并存的情况，例如：

- `DocumentQA`
- `documentQA`
- `docqa`

同时，任务类别、具体子任务、长度档位、文档标识、页面标识这几层概念也还有混用倾向。这样的问题看起来只是命名风格差异，但实际会影响：

- 配置项语义
- 页面与查询 ID 的构造
- Ground truth 映射
- 结果落盘与后续分析

v2 的建议不是规定某一种命名格式，而是要求先明确一套稳定的命名分层：哪些名称表示任务族，哪些名称表示具体子集，哪些名称表示长度档位，哪些名称表示文档或页面实体。只有这层关系先理清，后面的契约和配置才能真正稳定。

### 3.2 ID 契约的边界条件还不够清楚

当前文档已经强调了稳定 `page_id` / `query_id` 的必要性，这一点是对的。但仅仅“有稳定 ID”还不够，还需要明确这个 ID 需要覆盖到什么范围。

目前需要进一步澄清的问题是：

1. 不同长度档位之间是否共享同一套 ID 逻辑。
2. DocumentQA 内三个具体子任务之间如何避免命名冲突。
3. 后续若扩展到 VRAG、Summ 或其他子集，现有 ID 体系是否仍然成立。

也就是说，v2 更关注“ID 体系的适用边界”而不是“ID 长什么样”。如果这一点不提前说明，后面虽然可以跑通 baseline，但多子集比较、跨档位实验和结果合并时会反复返工。

### 3.3 检索范围与评测协议尚未完全显式化

当前计划已经明确使用 DocumentQA 作为主评测集，但仍缺一个关键设计决定：检索到底是在什么候选范围内进行。

DocumentQA 的数据形式天然更接近“单个查询对应单个长文档内的页面集合”。因此，设计文档需要进一步说明：

1. Baseline 是做文档内页级排序，还是把所有文档页面合成一个全局语料库后统一检索。
2. 三个 DocumentQA 子任务的结果是分别汇报，还是合并汇报。
3. 不同长度档位的实验是只选一个主档位，还是做多档位对比。

这些问题不属于实现细节，而属于评测协议本身。若协议不够明确，后续即使系统实现正确，结果也可能难以解释或难以和其他方案公平比较。

### 3.4 Phase 1 与 Phase 2 的依赖关系还不够对齐

当前 Phase 2 已经明确把 DocumentQA 作为 baseline 主评测集，但前面的环境与数据准备部分仍保留了较泛化的说法，例如先下载“一个任务图像包”或用 VRAG 做最小 smoke test。

这会带来一个计划层面的不对齐：

- Baseline 的实现依赖已经收敛到 DocumentQA。
- 但前置准备还没有把 DocumentQA 资源列为最明确的必选项。

v2 的建议是把这层依赖关系写清楚：如果 Phase 2 的主闭环依赖 DocumentQA，那么相应的数据资源、样本检查和路径验证就应在 Phase 1 中被明确前置，而不是停留在“任意任务包都可以”的层面。

### 3.5 索引存储策略的取舍还缺少反向约束说明

当前方案选择“每页独立存储”作为 baseline 索引策略，这在扩展性上有明显优点，尤其对后续的索引压缩和增量追加更友好。

但这一决策目前主要只写了优势，还缺一层反向说明：

- 小文件数量增长带来的 I/O 开销如何看待。
- Windows 文件系统下大量小文件是否会影响读写效率。
- 当页面规模继续增大时，这一策略是否仍然合适。

这里不一定要在文档里给出替代方案，但至少应把它描述为“当前阶段的优先策略及其权衡”，而不是默认它在所有规模下都天然最优。

### 3.6 某些接口仍混合了两套假设

当前设计一方面强调要兼容后续的变长 patch、索引压缩和两阶段检索，另一方面部分接口描述里又保留了明显偏向 baseline 的定长或全量假设。

这类混合主要体现为：

1. 有些能力更像是 baseline 便利函数。
2. 有些能力则被写成了长期设计不变量。

如果这两类假设不分开，后续扩展时就容易出现一种情况：接口表面上看支持扩展，实际却只有在 baseline 前提下才完全成立。

v2 的建议是把“当前阶段为了跑通 baseline 提供的便利能力”与“未来扩展也必须成立的核心抽象”分开表述。

### 3.7 配置层仍有语义混层现象

当前配置部分比原版完整得多，这是进步。但从设计角度看，配置项中仍混合了几种不同层面的信息：

- 数据选择
- 运行时参数
- 索引策略
- 检索策略
- ID 规则
- 路径组织

问题不在于这些信息能不能一起放在配置里，而在于文档还没有把它们的层次关系说明清楚。比如哪些属于实验切换参数，哪些属于项目级常量，哪些属于当前 baseline 的暂定策略。

v2 的建议是进一步强调配置项的语义分类，而不是继续补更多字段。配置要服务于复现和切换，而不是把每一个设计选择都直接硬编码成平级开关。

---

## 4. v2 修改方向

在保留当前整体方向的前提下，v2 建议重点补充以下几类说明。

### 4.1 明确命名分层

应把以下几个层次明确区分开：

1. 任务族
2. 具体子任务
3. 长度档位
4. 文档实体
5. 页面实体

这里不要求立即确定最终命名格式，但要求在全文中语义一致，不再混用。

### 4.2 明确评测协议

应在计划中显式说明：

1. 候选页面集合的范围如何定义。
2. Baseline 的主评测粒度是什么。
3. 多子任务、多档位结果如何组织与汇报。

这部分建议视为实验设计的一部分，而不仅仅是实现后的补充说明。

### 4.3 对齐阶段依赖

应让 Phase 1 的资源准备、样本检查和路径验证与 Phase 2 的 baseline 依赖保持一致。若主闭环依赖 DocumentQA，则前置资源准备应围绕 DocumentQA 展开。

### 4.4 将存储策略写成“阶段性选择”而非“天然结论”

当前索引方案可以保留，但建议增加一层表述：它是为当前 baseline 与后续扩展所做的优先选择，同时带有一定 I/O 和管理成本。这样后续若需要调整，不会与设计文本本身产生冲突。

### 4.5 区分核心抽象与便利实现

建议在设计说明中区分两类内容：

1. 必须长期成立的抽象边界。
2. 为了先跑通 baseline 而加入的便捷接口或实现假设。

这样有助于后续进阶方法接入时判断：哪些内容可以替换，哪些内容不应被破坏。

### 4.6 强化配置语义，而不是继续堆字段

配置层下一步更需要的是语义整理，而不是继续扩表。建议说明清楚：

1. 哪些参数用于实验切换。
2. 哪些参数用于环境复现。
3. 哪些参数属于当前阶段的策略选择。

这样能减少后续“改一个实验配置却牵动全局命名和路径”的问题。

---

## 5. 优先级建议

从实际影响看，v2 建议按以下优先级处理：

### 第一优先级

1. 命名分层与 ID 适用边界。
2. 检索范围与评测协议。
3. Phase 1 和 Phase 2 的依赖对齐。

这些问题会直接影响 baseline 是否能被正确实现和正确评估。

### 第二优先级

1. 存储策略的权衡说明。
2. baseline 假设与长期抽象的区分。

这些问题不会立即阻塞实现，但会影响 Phase 4 的扩展成本。

### 第三优先级

1. 配置层语义整理。

这部分更偏工程质量和复现质量，适合在 baseline 闭环基本稳定后进一步补齐。

---

## 6. 总结

如果不再把“设计文档写得过细”视为问题，那么当前 `Project_Plan.md` 已经基本符合 v1 的总体方向。

第二轮审查后，真正剩下的重点不再是模块拆得够不够细，而是以下几个更本质的问题：

1. 概念命名是否统一。
2. ID 契约是否覆盖到实验边界。
3. 评测协议是否清楚。
4. 阶段依赖是否前后一致。
5. 当前设计选择是否把权衡写明。

因此，v2 的作用不是再提出一套新的模块重构方案，而是推动设计文档从“方向正确”进一步走向“语义闭合、可执行且便于扩展”。
