# ZeroShotVDR Step 3.3 方向决策 v1

## 1. 目的

本文件用于完成 Phase 3 / Step 3.3：

1. 基于已经完成的稳定语义全量评测与 Step 3.2 分析，确定 Phase 4 的主改进方向；
2. 明确为什么当前不选择另一条候选路线作为主线；
3. 给出进入 Phase 4 前的实验口径与最小实现路径。

本轮决策基于以下现有产物：

- `outputs/eval_reports/step3_docqa_full_dual3090_stable_page_ids/`
- `outputs/eval_reports/step3_docqa_full_dual3090_stable_page_ids/analysis/`
- `docs/revision/step3_analysis_revision_v1.md`

## 2. 当前基线的可信结论

在修正 `page_id` 语义并将 Query 候选范围改为 sample-specific candidate pages 后，当前基线已经具备可进入 Phase 4 的稳定评测口径。

### 2.1 运行规模与效率

- 全量运行范围：15,577 queries / 3,653 docs / 87,922 pages
- 索引补建时间：6,689.0 s（约 1h51m29s）
- 检索时间：1,102.9 s（约 18m23s）
- 平均延迟：0.071 s/query
- P95 延迟：0.138 s/query
- 索引存储体量：约 88.6 GB

### 2.2 评测口径

当前需要同时保留两套结果，但主结论应建立在“有效标注子集”上：

1. **完整披露口径**：全量 15,577 条查询全部纳入统计；
2. **主比较口径**：排除 `no_ground_truth` 的 1,192 条查询，仅在 14,385 条有效标注查询上比较方法优劣。

之所以必须采用第二套口径做主表，是因为当前指标实现中，空 ground truth 会被记为完美召回与完美 MRR；若直接混入主表，会高估系统表现。

### 2.3 主比较口径下的当前基线

在 14,385 条有效标注查询上：

| k | Recall | Precision | MRR | nDCG |
| --- | --- | --- | --- | --- |
| 1 | 0.3342 | 0.4403 | 0.5838 | 0.4403 |

相对于旧的 provisional baseline，在同一有效标注子集上仍有显著提升：

这说明 Phase 3 的“稳定页面身份 + query-specific candidate scope”修正不是表面调参，而是修复了 baseline 的核心评测语义。

## 3. Step 3.2 暴露出的真实瓶颈

当前 bad case 的主要热点如下：

| subtask | length | queries_with_ground_truth | bad_case_rate | mean_candidate_pages |
| --- | --- | --- | --- | --- |
| slidevqa | K128 | 1047 | 0.5196 | 135.22 |
| slidevqa | K64 | 1047 | 0.4690 | 67.16 |
| slidevqa | K32 | 1047 | 0.4183 | 33.16 |
| slidevqa | K16 | 1041 | 0.2968 | 16.23 |
| mmlongdoc | K128 | 726 | 0.2548 | 56.43 |
| longdocurl | K128 | 1153 | 0.2229 | 55.31 |

从当前分析可以提炼出三个与 Phase 4 直接相关的现象：

### 3.1 长上下文退化与候选规模高度相关

最难的 slice 基本都集中在：

- K64 / K128
- slidevqa 与 mmlongdoc
- 候选页数显著高于平均值的样本

这说明当前 baseline 的问题不只是“语义不够强”，还包括候选页过多时，full MaxSim 精排更容易被相邻版式页和视觉模板页干扰。

### 3.2 slidevqa 以 `miss_top10` 为主，不是多页召回不足为主

在 slidevqa 的 K32-K128 区段，bad case 以 `miss_top10` 为主，而不是 `multi_page_partial` 为主。这更像是：

- 目标页在大候选集里被相似版式页淹没；
- baseline 对“粗粒度语义相近但细节不同”的 slide 识别不够稳定。

### 3.3 longdocurl / mmlongdoc 中仍有明显的邻页与多页证据问题

longdocurl 和 mmlongdoc 的长上下文 bad case 中，`multi_page_partial` 占比不低，说明：

- 相邻页扩展仍然有价值；
- 许多查询需要保留多个高置信候选，而不是只做单页命中。

这使得任何会粗暴丢失细粒度证据的压缩方案都存在更高风险。

## 4. 候选方向对比

### 4.1 方向 A：查询感知的自适应索引压缩

**优点**：

- 直接回应当前索引体量约 88.6 GB 的问题；
- 理论上可同时降低存储、I/O 与 MaxSim 打分成本；
- 与课程要求中的“索引构建、存储成本与推理开销平衡”高度一致。

**当前阶段的主要风险**：

1. 当前 hardest slices 正好是视觉细节密集、相邻页极易混淆的场景；
2. 若 patch pruning 过早做为主线，容易进一步损伤 slidevqa 与多页证据任务；
3. 需要同时处理 patch 重要性定义、变长 patch 存储、重建索引与多轮压缩率实验，实验面较大；
4. Phase 3 刚完成评测语义稳定化，此时再大改底层页面表示，容易把“评测口径切换”和“方法效果变化”混在一起。

结论：方向 A 很有价值，但更适合在已有更稳定的 Phase 4 主线之后，作为附加压缩实验或 Phase 4 后半段的补充。

### 4.2 方向 B：两阶段粗精检索

**优点**：

1. 当前代码已经具备直接落地的扩展点：
   - `IndexStore.get_mean_pooled_view()` 已存在；
   - `RetrievalPipeline` 已支持 `candidate_strategy="mean_pool_topN"`；
   - baseline 的四阶段流水线无需重写，只需替换候选阶段策略；
2. Step 3.2 的主要热点与“大候选集中的相似页混淆”高度一致，方向 B 可以直接针对这一点；
3. 可以同时优化：
   - 延迟：减少进入 full MaxSim 的页面数；
   - 稳定性：先用粗筛排除明显无关页面，再让精排专注于更小候选集；
4. 更容易设计为“逐步增强”的原创方法，而不是简单复现标准 top-50 two-stage。

**潜在缺点**：

- 若粗筛质量差，可能导致真正相关页在第二阶段前就被截断；
- 需要 carefully 选择候选规模，否则性能会退化。

结论：方向 B 的风险更可控，且与当前代码和失败分析的贴合度更高，适合作为 Phase 4 主线。

---

## 5. 最终决策

### 5.1 主方向：方向 B，但不是“固定 top-50”的朴素版本

Phase 4 主线确定为：

**查询自适应的两阶段粗精检索（query-adaptive coarse-to-fine retrieval）**。

它属于 Project Plan 中方向 B 的延伸，但会加入两个当前分析直接支持的增强点：

1. **自适应候选规模**
   - 不使用固定 top-50；
   - 候选规模由原始候选页数、粗筛分数分布和保守阈值共同决定；
   - 目标是在 K4-K8 短上下文上避免无意义粗筛，在 K64-K128 上显著减小精排范围。

2. **邻页扩展机制**
   - 对 coarse stage 中排名靠前的页面，按稳定 source page index 做有限窗口扩展；
   - 目的不是扩大到整文档，而是补偿 longdocurl / mmlongdoc 中常见的相邻页和多页证据需求。

这两点能够让 Phase 4 不只是“把 top-50 加到 pipeline 里”，而是形成一个有明确失败分析来源的、面向当前数据集特性的原创方案。

### 5.2 方向 A 的处理方式

方向 A 不放弃，但降为：

- 若主线 B 完成较快，则将 A 作为小规模补充实验；
- 否则仅在最终报告中作为“下一步工作”讨论，不作为本轮主线实现。

---

## 6. Phase 4 的最低实现路径

为控制风险，Phase 4 建议按以下顺序推进：

### 6.1 第一阶段：做出可运行的两阶段主路径

- 新增 `src/zeroshot_vdr/advanced/two_stage.py`
- 将粗筛逻辑从 `RetrievalPipeline` 的预留分支中抽离为可配置策略
- 支持：
  - `top_n` 固定版本
  - `adaptive_top_n` 版本
  - 邻页扩展开关

### 6.2 第二阶段：在有效标注子集上做参数搜索

重点探索：

- `top_n` 或阈值的保守范围
- 邻页扩展窗口大小（如 ±1 / ±2）
- 是否对 slidevqa 与非 slidevqa 使用不同策略

### 6.3 第三阶段：只保留最有说服力的比较表

最终主表建议至少包含：

1. Baseline（稳定 page id 版本）
2. Two-stage fixed top-N
3. Two-stage adaptive top-N
4. Two-stage adaptive top-N + neighbor expansion

并统一在 14,385 条有效标注查询上比较。

---

## 7. 进入 Phase 4 前的汇报口径

为避免后续表格口径混乱，当前建议正式固定如下：

1. **主表口径**：仅统计有效标注查询；
2. **附录口径**：保留全量查询结果，以示完整披露；
3. **bad case 分析**：将 `no_ground_truth` 单列，不计入真实 bad case；
4. **方法对比**：新旧方法必须在同一有效标注子集上比较。

这四点一旦固定，Phase 4 之后的主表、消融表和结论段就不会再因口径变化而反复重写。

---

## 8. 结论

Step 3.3 的最终决策是：

- **主线采用方向 B：查询自适应的两阶段粗精检索**；
- **方向 A 暂不作为主线，只保留为补充实验或未来工作**；
- **Phase 4 的主评测口径固定为有效标注子集 14,385 queries**。

这一路线兼顾了：

1. 与当前失败分析最直接对应；
2. 与现有代码结构最贴合；
3. 在有限时间内做出可比较、可解释、可复现结果的成功概率最高。
