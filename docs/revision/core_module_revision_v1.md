# ZeroShotVDR 核心模块修订建议 v1

## 1. 目的与范围

本文基于以下材料进行修订建议整理：

- `docs/Project_Plan.md` 中的核心模块接口设计与 Phase 2-4 计划
- `docs/MMLongBench_Dataset_Notes.md` 中对 MMLongBench 的任务适配分析
- 当前仓库的实际包结构、配置文件和环境脚本

目标不是推翻现有方案，而是在尽量保留 ColPali baseline 路线的前提下，修正几个会阻碍 Phase 2 实现和 Phase 4 扩展的设计问题，使核心模块同时满足以下三点：

1. 能直接支撑基于 DocumentQA 的页级检索 baseline。
2. 能平滑扩展到查询感知索引压缩与两阶段检索。
3. 能与当前仓库的 `src/zeroshot_vdr/` 包结构、Windows 环境约束和配置方式保持一致。

---

## 2. 当前设计的主要问题

### 2.1 预处理层过度绑定 PDF 输入

当前设计将 `preprocess.py` 定义为 PDF 页面渲染器，核心入口围绕 `pdf_dir -> page image -> metadata` 展开。这一设计对从原始 PDF 构建页面图像是成立的，但对当前项目的主评测集 DocumentQA 并不贴合。

MMLongBench 的 DocumentQA 子集已经直接提供：

- `page_list`：页面图像路径列表
- `ans_page_list`：答案所在页面编号列表

因此，Phase 2 的主路径更像是“数据集适配 + 页面语料构建”，而不是“PDF 渲染”。如果继续把预处理层定义成 PDF-only，后续实现中还要额外补一个数据适配层，模块职责会被拆碎。

### 2.2 模块路径与当前仓库包结构不一致

计划文档多处将模块写成：

- `src/preprocess.py`
- `src/indexer.py`
- `src/retriever.py`
- `src/evaluator.py`

但当前仓库是标准的 `src/zeroshot_vdr/` 包布局。后续若继续按文档原样落地，代码会散在包外，不利于导入、测试、脚本入口和未来复用。

### 2.3 页面唯一标识没有形成稳定契约

当前设计中：

- Retriever 返回 `doc_id, page_idx, score`
- Evaluator 的指标函数则假设输入是 `relevant_page_id` 这样的字符串集合

这意味着“页面唯一标识”的拼接规则没有被明确建模。对于单一子任务也许还能临时拼接，但一旦扩展到多任务、多长度档位、不同文档来源，评测和结果落盘都会变脆弱。

### 2.4 索引存储形式不利于增量更新和进阶方法

当前设计把索引核心存储固定成单一 `embeddings.pt`，形状为 `[n_pages, n_patches, dim]`，同时又希望支持 `incremental_update()`。

这个组合存在两个问题：

1. 单文件张量不适合真增量追加，新增页面时通常需要重写整份索引。
2. 一旦引入 patch pruning，不同页面保留的 patch 数可能不再固定，单一规则张量会变得不自然。

这会让 Phase 4 的“压缩索引”和“两阶段粗排视图”难以复用同一底层存储。

### 2.5 Retriever 抽象只覆盖了 baseline，不覆盖检索流水线

当前 `ColPaliRetriever` 的抽象接近“一个模型 + 一个索引张量 + 一个 MaxSim 排序函数”。它可以支持 baseline，但对两阶段检索不够自然。

两阶段检索实际上包含至少四个步骤：

1. 查询编码
2. 候选生成
3. 精排打分
4. 结果组装

如果这些步骤都揉在同一个 Retriever 里，Phase 4 很可能需要复制一套新类，而不是在同一框架里替换组件。

### 2.6 配置层过薄，实验参数会散落成硬编码

当前 `config/default.yaml` 只有渲染参数，但实际项目已经至少存在以下配置需求：

- 数据根目录和任务选择
- Hugging Face 缓存路径
- model repo 与 processor repo
- batch size / dtype / device
- 索引构建参数
- 检索参数和评测参数
- 进阶方法参数

如果这些配置不尽早集中管理，后续脚本、模块和 notebook 会很快出现重复硬编码。

### 2.7 Windows 环境下的导入顺序约束尚未进入模块边界设计

当前环境脚本已经验证：在 Windows 上，`datasets`/`pandas` 与 `torch` 的导入顺序有要求。若在同一进程中先导入 `torch`，再导入 `datasets`，可能出现 access violation。

这不是单纯的实现细节，而是核心模块在拆分时就必须规避的问题。数据读取层和模型层若长期混在同一模块顶部导入，后面会反复踩坑。

## 3. 修订目标

v1 修订建议更适合作为“方向性文档”，而不是实现规范。其目标应聚焦在以下几点：

1. 明确当前设计中哪些地方会阻碍 baseline 落地。
2. 给出一套足够稳定、但不过度约束实现方式的核心框架。
3. 为后续进阶方法保留扩展空间，而不是提前锁定具体实现细节。
4. 让模块边界、数据契约和配置职责更清晰，减少后续返工。

---

## 4. 核心框架

这份修订不必预先规定精确的目录树、类名或文件名，但建议核心设计至少覆盖以下几层：

1. 数据接入层
   负责将不同来源的样本组织方式转成统一的页面语料与查询语料。
2. 表示与索引层
   负责页面编码、索引持久化，以及不同检索视角下的索引组织。
3. 检索执行层
   负责查询编码、候选生成、相关性打分和结果排序。
4. 评测与分析层
   负责统一评测输入、指标计算和结果分析。
5. 配置与运行时支撑
   负责实验参数、环境约束、路径管理和复现支持。

这一框架的关键点不在于如何命名模块，而在于各层之间的职责清晰且依赖方向单一。只要满足这一点，具体代码组织可以保留一定灵活性。

---

## 5. 统一数据契约的方向

当前设计里，一个核心问题是页面、查询、检索结果、评测标注之间缺少稳定契约。修订时更值得强调原则，而不是先规定具体字段模板。

建议至少确保以下几点：

1. 页面应有稳定的唯一标识，且这一标识能贯穿索引、检索和评测。
2. 查询也应有稳定标识，避免结果落盘和指标统计阶段再临时拼接。
3. 检索结果需要保留最基本的可追踪信息，例如命中对象、分数和排序位置。
4. ground truth 和 retrieval result 的主键体系应一致，否则评测层会不断做额外适配。

这里不必提前锁定某种字符串格式或某种数据类定义，但必须先统一“什么是系统中的最小主键单位”。否则后续所有模块都会出现隐式耦合。

---

## 6. 预处理层修订建议

预处理层最需要调整的不是具体 API，而是职责定位。

修改方向应是：

1. 从“PDF 渲染”转向“语料构建”。
2. 把数据来源差异封装在接入侧，而不是传播到索引、检索和评测层。
3. 让主评测集的接入路径尽量直接，避免 baseline 一开始就绕远路。

也就是说，预处理层应优先回答“如何把不同数据来源转成统一页面语料”，而不是预设所有输入都来自 PDF。至于是否采用适配器、工厂或其他组织方式，可以留给实现阶段决定。

---

## 7. 索引层修订建议

索引层当前最值得修正的是设计思路，而不是落盘细节。

建议强调以下方向：

1. 编码、存储和检索视角最好在抽象上区分开，不要默认它们永远是一回事。
2. 索引组织应能兼容 baseline 和后续压缩、粗排等扩展场景。
3. 不宜过早把系统绑定到单一的存储形式，否则后续一改就会牵动整条链路。

对于增量更新，也不必在 v1 就给出强承诺。更合理的表述是：优先保证索引构建与加载路径清晰可用，再根据实际需求决定是否引入更复杂的增量策略。

---

## 8. 检索层修订建议

检索层的问题在于，当前设计更像一个“baseline 检索器”，而不是一个可扩展的检索框架。

修改方向应当是：

1. 将查询表示、候选召回、相关性计算和结果组装视为可区分的环节。
2. baseline 可以是这些环节的一种最简组合，但不应成为整个抽象的唯一形态。
3. 进阶方法应尽量表现为局部替换或局部增强，而不是复制一套并行系统。

只要这一点成立，两阶段检索和索引压缩都更容易落在同一框架内。文档不需要提前规定具体组件名或调用方式，但应明确“检索不是单一步骤”。

---

## 9. 评测层修订建议

评测层建议保留两个核心原则：

1. 指标计算应尽量独立于具体数据集。
2. 数据集适配应尽量独立于具体指标实现。

这样做的原因很简单：后续如果引入新的评测子集，最好只改 ground truth 的构造方式，而不是连指标逻辑一起改动。文档在这里不必预先规定某种结果对象或某种函数签名，但应明确分层思路。

---

## 10. 配置层修订建议

配置层的关键不是配置文件长什么样，而是哪些事情不应继续散落在脚本和模块内部。

建议至少将以下几类信息纳入统一配置管理：

1. 数据来源与任务选择。
2. 模型与运行时设置。
3. 索引构建与检索的主要参数。
4. 评测和实验切换所需的控制项。

换句话说，配置层应服务于复现和实验切换，而不是只承担少量静态参数存放的角色。至于最终使用单文件 YAML、分层配置还是其他方式，可以不在 v1 中写死。

---

## 11. Windows 环境约束的设计落点

建议在模块边界层面就显式规定：

1. `data/` 层可以依赖 `datasets`/`pandas`，但应避免在模块顶层同时导入 `torch`。
2. `models/`、`indexing/`、`retrieval/` 层主要依赖 `torch`，应尽量不在模块顶层导入 `datasets`。
3. 若某模块必须同时使用二者，应遵守“先 datasets/pandas，后 torch”的导入顺序。

这个约束建议写进后续模块头部说明或开发说明中，否则很容易在实现阶段被忽略。

---

## 12. 对两类进阶方法的扩展性结论

### 12.1 查询感知索引压缩

如果按上述方向修订，查询感知索引压缩更容易作为“索引层或打分层的局部变化”接入，而不必重做整个系统。这一点的关键不在某种具体实现，而在于索引组织和检索流程本身已经预留了变化空间。

### 12.2 两阶段粗精检索

同样地，两阶段检索也应尽量表现为检索流程中的分层执行，而不是一个完全独立的新系统。只要候选召回和精排本身在框架上是可区分的，后续引入粗排阶段就不会破坏 baseline 结构。

### 12.3 扩展性判断

修订后的设计对进阶方法的支持会明显优于原方案，原因不是规定了更多模块，而是更早建立了几项共用基础：

1. 稳定 ID 契约
2. 可扩展的索引组织方式
3. 可分层的检索流程

---

## 13. 建议的落地顺序

建议的推进顺序可以保持原则性描述：

1. 先打通主评测集上的 baseline 闭环。
2. 再补足结果分析、复现和实验管理能力。
3. 最后在不破坏 baseline 主链路的前提下接入进阶方法。

这样的顺序有助于控制复杂度，也更符合课程项目的实际节奏。

---

## 14. 建议的接口替换摘要

从设计意图上看，v1 更推荐完成以下几类替换：

1. 从单一输入假设转向统一语料视角。
2. 从单一索引文件思维转向可扩展的索引组织思维。
3. 从“一个检索器做完所有事”转向分层检索流程。
4. 从临时拼接结果字段转向统一数据契约。

这里强调的是替换方向，而不是某组固定类名或固定接口签名。

---

## 15. 最终建议

综合判断，现有设计可以作为 baseline 的雏形，但如果不做修订，会在以下三个位置最先暴露问题：

1. 用 DocumentQA 起步时，预处理层与真实数据组织不匹配。
2. 做 Phase 4 时，索引和 Retriever 的抽象不够承载多视图与两阶段流程。
3. 做评测与结果分析时，页面 ID 和结果格式不统一，容易引入隐性错误。

因此，建议将本 v1 修订作为后续实现的统一蓝图：

- Phase 2 先落地 DocumentQA baseline
- 所有实现统一收敛到 `zeroshot_vdr` 包内
- 索引与检索从第一版起就按“多视图 + 流水线”思路搭框架

这样做能在不显著增加 Phase 2 开发成本的前提下，为 Phase 4 的原创改进方法预留足够扩展空间。
